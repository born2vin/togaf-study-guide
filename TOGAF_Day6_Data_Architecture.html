Phase C covers the Information Systems Architectures: Data and Application. TOGAF lets you develop them in either order, or in parallel. Today covers the Data Architecture; tomorrow covers Application.

01Purpose of Phase C (Data)

The Data Architecture describes the structure of an organization's logical and physical data assets and data management resources.
Business ArchitecturePhase B
↓ is enabled by
Data ArchitecturePhase C
↓ is used by
Application ArchitecturePhase C

02Objectives

  • Develop the Target Data Architecture that enables the Business Architecture and the Architecture Vision, while addressing the Request for Architecture Work and stakeholder concerns.
  • Identify candidate Architecture Roadmap components based on gaps between the Baseline and Target Data Architectures.

The steps are the same nine common steps used in Phases B and D.

03Key Considerations

Data management

A clear data management approach helps the enterprise use data as a strategic asset. The architecture should answer questions such as:

  • Which application components will act as the system of record or reference for enterprise master data?
  • Will there be an enterprise-wide standard that all applications, including packages, must adopt?
  • How are data entities used by business functions, processes and services?
  • How and where is data created, stored, transported and reported?
  • What level and complexity of data transformation is needed?

Data migration

When a new application replaces an existing one, data must be migrated. The Data Architecture should identify data migration requirements, including data quality, data cleansing, and the transformation needed to fit the new applications.

Data governance

Data governance makes sure the enterprise has the necessary dimensions in place to enable data transformation:

DimensionWhat it covers
StructureWhether the organization has the structure and standards to manage data entities
Management systemWhether the enterprise has the management systems and data-related programmes to manage data governance
PeopleWhether the enterprise has the data-related skills and roles it needs

04Data Models and Reference Models

LevelPurpose
ConceptualThe key business entities and how they relate; understood by business stakeholders
LogicalEntities, attributes and relationships in more detail, independent of any specific database technology
PhysicalHow data is actually stored in specific technologies; usually a solution-level concern

Industry reference models can speed up Data Architecture work. Examples include ARTS (retail) and Energistics (energy), as well as industry-specific data models from standards bodies.

05Outputs

  • Refined Phase A deliverables
  • Draft Architecture Definition Document, with Baseline and Target Data Architecture and relevant views
  • Draft Architecture Requirements Specification, including gap analysis results and data interoperability requirements
  • Data Architecture components of an Architecture Roadmap

06Artifacts Typically Produced

TypePhase C (Data) artifacts
CatalogData Entity/Data Component catalog
MatricesData Entity/Business Function matrix · Application/Data matrix
DiagramsConceptual Data · Logical Data · Data Dissemination · Data Security · Data Migration · Data Lifecycle
The Data Entity/Business Function matrix links Phase B and Phase C: it shows which business functions use which data, and helps assign data ownership (data trustees).
The Data Security diagram shows which actors can access which data, while the Data Dissemination diagram shows how data is spread across application components and where it physically lives. Don't mix them up.

The takeaway

  • Phase C covers Data and Application Architecture, in either order or in parallel.
  • Data Architecture describes logical and physical data assets and data management resources.
  • Key considerations: data management, data migration, and data governance (structure, management system, people).
  • Data models run from conceptual to logical to physical.
  • Key artifacts: Data Entity/Data Component catalog, Data Entity/Business Function matrix, and the Conceptual, Logical, Dissemination, Security, Migration and Lifecycle diagrams.
