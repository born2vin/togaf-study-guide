Yesterday covered the data side of Phase C. Today covers the other half: the Application Architecture, which describes the applications the enterprise needs to process its data and support its business.

01Purpose of Phase C (Application)

The Application Architecture provides a blueprint for the individual applications to be deployed, their interactions, and their relationships to the core business processes of the organization.

It defines the kinds of application systems needed: logical groups of capabilities that manage the data objects in the Data Architecture and support the business functions in the Business Architecture. It is not primarily about choosing products; it describes what applications must do.

02Objectives

  • Develop the Target Application Architecture that enables the Business Architecture and the Architecture Vision, while addressing the Request for Architecture Work and stakeholder concerns.
  • Identify candidate Architecture Roadmap components based on gaps between the Baseline and Target Application Architectures.

The steps are the same nine common steps used in Phases B, C (Data) and D.

03Reference Models

  • Integrated Information Infrastructure Reference Model (III-RM): a TOGAF reference model, published as a Series Guide, focused on the application-level components and services needed for Boundaryless Information Flow™, meaning getting the right information to the right people at the right time, securely.
  • Industry application reference models, where available, such as models for telecoms or retail.
  • The organization's own existing application portfolio and standards in the Architecture Repository.
The III-RM is a subset of the TOGAF Technical Reference Model (TRM): it expands the TRM's application software and application platform areas. Both are covered on Day 22.

04Interoperability and Integration

The Application Architecture must show how applications work together. TOGAF encourages defining interoperability early, because integration problems are expensive to fix later. Typical questions include:

  • Which applications must exchange information, and in what form?
  • Which interfaces exist today, and which are needed in the Target?
  • Can shared services replace point-to-point integrations?

Detailed interoperability requirements are consolidated and reconciled in Phase E.

05Typical Application Gaps

Application gap analysis uses the same matrix technique as Phase B. Common findings include:

  • Missing applications: capabilities needed in the Target with no application today
  • Redundant applications: several applications doing the same job, which are candidates for consolidation
  • Applications to retire: Baseline applications not needed in the Target
  • Interface gaps: missing or inadequate connections between applications

06Outputs

  • Refined Phase A deliverables
  • Draft Architecture Definition Document, with Baseline and Target Application Architecture and relevant views
  • Draft Architecture Requirements Specification, including gap analysis results, application interoperability requirements, and constraints on the Technology Architecture
  • Application Architecture components of an Architecture Roadmap

07Artifacts Typically Produced

TypePhase C (Application) artifacts
CatalogsApplication Portfolio catalog · Interface catalog
MatricesApplication/Organization · Role/Application · Application/Function · Application Interaction
DiagramsApplication Communication · Application and User Location · Application Use-Case · Enterprise Manageability · Process/Application Realization · Software Engineering · Application Migration · Software Distribution
The Application Interaction matrix and the Application Communication diagram both describe how applications communicate. The matrix is a grid of which applications talk to which; the diagram is a picture of the communication paths and interfaces.

The takeaway

  • Application Architecture is a blueprint for individual applications, their interactions, and their links to business processes.
  • It defines the kinds of applications needed, not specific products.
  • The III-RM supports Boundaryless Information Flow and is a subset of the TRM.
  • Gap analysis finds missing, redundant and retiring applications and interface gaps.
  • Key artifacts: Application Portfolio and Interface catalogs, Application/Function and Application Interaction matrices, and the Application Communication diagram.
