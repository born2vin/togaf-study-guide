Phase D: Technology Architecture

Platforms and infrastructure, the Technical Reference Model, key technology considerations and artifacts

Phase D completes the architecture domains. The Technology Architecture describes the platforms and infrastructure that will host the applications and data defined in Phase C.

01Purpose of Phase D

The Technology Architecture describes the software and hardware capabilities needed to support the deployment of business, data and application services. This includes IT infrastructure, middleware, networks, communications, processing and standards.

02Objectives

  • Develop the Target Technology Architecture that enables the logical and physical application and data components and the Architecture Vision, while addressing the Request for Architecture Work and stakeholder concerns.
  • Identify candidate Architecture Roadmap components based on gaps between the Baseline and Target Technology Architectures.

The steps are the same nine common steps used in Phases B and C.

03Reference Models and Standards

  • TOGAF Technical Reference Model (TRM): a generic Foundation Architecture that provides a taxonomy of platform services. It is now published as a Series Guide. Its main elements are Application Software, the Application Platform and the Communications Infrastructure, joined by the Application Platform Interface and the Communications Infrastructure Interface.
  • The organization's own Standards Information Base in the Architecture Repository: technology standards that projects must follow.
  • Industry and vendor reference architectures, such as cloud provider reference architectures.
The TRM is a Foundation Architecture in the Enterprise Continuum: generic and reusable by any organization. The Enterprise Continuum is covered on Day 19.

04Key Technology Considerations

ConsiderationTypical questions
Emerging technologiesCan new technologies, such as cloud, containers or AI platforms, deliver business value or reduce cost?
Performance and capacityWill the platforms handle expected volumes and growth?
Availability and resilienceWhat service levels and recovery times are needed?
Location and latencyWhere must components be hosted, and what network latency is acceptable?
Maintainability and standardsDoes the Target reduce technical diversity and follow the approved standards?
SecurityHow are infrastructure-level security controls provided?
The TOGAF example principle Control Technical Diversity applies strongly here: limiting the number of supported platforms reduces cost and complexity.

05Outputs

  • Refined Phase A deliverables
  • Draft Architecture Definition Document, with Baseline and Target Technology Architecture and relevant views
  • Draft Architecture Requirements Specification, including gap analysis results and requirements for the technology
  • Technology Architecture components of an Architecture Roadmap
Phase D is the last of the architecture-development phases. After it, the Architecture Definition Document and Architecture Requirements Specification cover all four domains. They are then used in Phase E to plan implementation.

06Artifacts Typically Produced

TypePhase D artifacts
CatalogsTechnology Standards catalog · Technology Portfolio catalog
MatrixApplication/Technology matrix
DiagramsEnvironments and Locations · Platform Decomposition · Processing · Networked Computing/Hardware · Network and Communications
  • Technology Standards catalog: the agreed standards for technology across the enterprise.
  • Technology Portfolio catalog: all the technology in use, such as platforms, products and versions.
  • Application/Technology matrix: which applications run on which technology.
  • Environments and Locations diagram: which locations host which applications and technology, and in which environments (e.g. development, test, production).
  • Platform Decomposition diagram: the technology platform broken down into its components.

The takeaway

  • Technology Architecture describes the software and hardware capabilities that host business, data and application services.
  • Phase D uses the same nine common steps as Phases B and C, and is the last architecture-development phase.
  • The TRM is a generic Foundation Architecture: Application Software, Application Platform and Communications Infrastructure.
  • Key considerations include emerging technology, performance, availability, location and latency, and controlling technical diversity.
  • Key artifacts: Technology Standards and Technology Portfolio catalogs, the Application/Technology matrix, and the Environments and Locations and Platform Decomposition diagrams.
