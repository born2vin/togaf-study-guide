Yesterday covered the big picture. Today covers the words TOGAF uses to describe architecture work. Foundation questions test these definitions closely, and the options are often very similar. Learn the exact wording and the differences between terms.

1. Stakeholders and Concerns

TOGAF takes these definitions from ISO/IEC/IEEE 42010.

Stakeholder: an individual, team, organization, or class thereof, having an interest in a system.
Examples: CEO, CFO, CIO, business process owners, end users, regulators, project managers, suppliers.
Concern: an interest in a system that matters to one or more stakeholders.
Examples: performance, reliability, security, cost, compliance, scalability, ease of change.

A concern is what a stakeholder cares about. It is not a document or a diagram. Stakeholders are identified in the Preliminary Phase and Phase A. How to manage them is covered on Day 15.

This is the pair most often confused in exams.

Architecture Description is a related term. It is the collection of artifacts that documents an architecture. An architecture description is made up of views.

3. Deliverables, Artifacts and Building Blocks

These three terms form the backbone of TOGAF's Architecture Content Framework.

Deliverable

A work product that is contractually specified, then formally reviewed, agreed and signed off by stakeholders.
  • Examples: Statement of Architecture Work, Architecture Definition Document, Architecture Requirements Specification, Architecture Roadmap.
  • Deliverables are outputs of projects.
  • When a project ends, a deliverable is either archived, or transitioned into the Architecture Repository as a reference model, a standard, or a snapshot of the Architecture Landscape.

Artifact

A more granular work product that describes one aspect of the architecture. There are three types:

TypeWhat it showsExample
CatalogA list of building blocks of one typeApplication Portfolio Catalog
MatrixRelationships between building blocks, in a gridApplication/Function Matrix
DiagramA picture of building blocks and how they relateApplication Communication Diagram

Building Block

A potentially reusable component of enterprise capability. It can be combined with other building blocks to deliver architectures and solutions.
Architecture Building Block (ABB)Solution Building Block (SBB)
NatureDescribes the required capabilityDescribes the actual component that implements it
Product/vendorProduct- and vendor-neutralProduct- or vendor-aware
RoleCaptures requirements; directs and guides SBB developmentImplements the capability defined by ABBs
Example"Customer Relationship Management capability""Salesforce Sales Cloud, configured as…"

Features of a good building block:

  • It has a defined boundary and is recognisable as one thing.
  • It has published, well-defined interfaces.
  • It can be made from other building blocks, or be part of a larger one.
  • Ideally, it is reusable and replaceable.
  • It can be defined at different levels of detail.
  • It is not necessarily software. It can be a process, a role, a data entity or a platform.

4. Architecture States: Baseline, Target, Transition, Gap

TermMeaning
Baseline ArchitectureThe existing, defined architecture before a change ("as-is")
Target ArchitectureThe description of a future state ("to-be")
Transition ArchitectureA formal description of one state of the architecture at an architecturally significant point in time. It shows an intermediate step between Baseline and Target.
GapA statement of the difference between two states. Gap Analysis is used in Phases B, C and D.

Transition Architectures are mainly developed in Phases E and F. They let organizations deliver business value in steps instead of making one big change.

5. Two More Useful Terms

  • Capability: an ability that an organization, person or system possesses, such as "Online Payment Processing."
  • Architecture Repository: where architecture outputs are stored. It is covered on Day 19.

The takeaway

  • Stakeholders have concerns.
  • A viewpoint defines the conventions for a view, and a view addresses those concerns.
  • Deliverables are formally signed off. They contain artifacts: catalogs (lists), matrices (relationships) and diagrams (pictures). Artifacts describe building blocks.
  • ABBs are vendor-neutral and define what is needed. SBBs are product-aware and define how it is implemented.
  • Architecture moves from Baseline to Target through Transition Architectures. The Gap is the difference between two states.
