With the four domains defined, the ADM turns towards delivery. Phase E is the first phase directly concerned with implementation: it works out how to get from the Baseline to the Target.

1. Purpose of Phase E

Phase E describes the process of identifying delivery vehicles (projects, programmes or portfolios) that effectively deliver the Target Architecture identified in the previous phases. It creates the initial complete version of the Architecture Roadmap.

Phase E consolidates the gaps from Phases B, C and D, groups them into work packages, and decides whether an incremental approach using Transition Architectures is needed.

2. Objectives

  • Generate the initial complete version of the Architecture Roadmap, based on the gap analysis and candidate roadmap components from Phases B, C and D.
  • Determine whether an incremental approach is required, and if so identify Transition Architectures that will deliver continuous business value.

3. Steps

  1. Determine or confirm key corporate change attributes
  2. Determine business constraints for implementation
  3. Review and consolidate gap analysis results from Phases B to D
  4. Review consolidated requirements across related business functions
  5. Consolidate and reconcile interoperability requirements
  6. Refine and validate dependencies
  7. Confirm readiness and risk for business transformation
  8. Formulate the Implementation and Migration Strategy
  9. Identify and group major work packages
  10. Identify Transition Architectures
  11. Create the Architecture Roadmap and Implementation and Migration Plan

4. Implementation and Migration Strategy

Basic strategy

StrategyMeaning
GreenfieldStart from the beginning, with no existing environment to migrate from
RevolutionaryA radical change: switch over from old to new in one step (a "big bang")
EvolutionaryConvergent, phased change delivered in increments, usually through Transition Architectures

Implementation approach

  • Build, buy or reuse for each solution: develop in-house, buy a commercial product (COTS), or reuse existing assets
  • Outsourcing or open-source options where relevant

5. Key Techniques and Tables

TechniquePurpose
Consolidated Gaps, Solutions and Dependencies matrixBrings together all gaps from Phases B–D with potential solutions and their dependencies
Implementation Factor Assessment and Deduction matrixRecords factors that affect the implementation (risks, issues, assumptions, dependencies), with their descriptions, deductions and impacts
Architecture Definition Increments tableLists the projects and the increments (Transition Architectures) each will deliver
Transition Architecture State Evolution tableShows the state of each architecture building block in each Transition Architecture
Business Value AssessmentA matrix of value against risk to help prioritise work packages
Each Transition Architecture should deliver business value on its own. If a step delivers nothing useful, it is usually not a good transition point.

6. Outputs

  • Refined and updated Phase A deliverables
  • Updated Architecture Definition Document and Architecture Requirements Specification
  • Capability Assessment
  • Architecture Roadmap: work package portfolio, identification of Transition Architectures, and implementation recommendations
  • Transition Architectures
  • Implementation and Migration Plan (version 0.1): the implementation and migration strategy and initial project charters
Phase E creates only an initial version of the Implementation and Migration Plan. It is finalized in Phase F. Exam questions often test which phase creates and which finalizes.

7. Artifacts Typically Produced

  • Project Context diagram: shows the scope of a work package and its links to organizations, functions, services, processes, applications, data and technology
  • Benefits diagram: shows opportunities identified in an architecture definition, classified by size, complexity and benefit

The takeaway

  • Phase E is the first phase directly concerned with implementation.
  • It creates the initial complete Architecture Roadmap and decides whether Transition Architectures are needed.
  • It consolidates gaps, requirements, interoperability and dependencies from Phases B–D, then groups them into work packages.
  • Basic strategies: Greenfield, Revolutionary, Evolutionary; approaches include build, buy or reuse.
  • It produces version 0.1 of the Implementation and Migration Plan, which is finalized in Phase F.
