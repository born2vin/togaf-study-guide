The ADM tells you how and when to develop an architecture. The Architecture Content Framework tells you what to produce. Today covers that framework and the content metamodel beneath it.

1. Purpose of the Architecture Content Framework

The Architecture Content Framework provides a structural model for architectural content, so that the major work products can be consistently defined, structured and presented.
  • It gives a detailed model of the outputs, so architects in different teams produce compatible work.
  • It shows the relationships between content, so the architecture can be traced from drivers to implementation.
  • It can be used with the ADM or with other frameworks; it is not tied to one notation or tool.

3. The Content Metamodel

The content metamodel defines a formal structure for the terms used in architecture, the entities and the relationships between them, to ensure consistency, completeness and traceability.

It answers questions such as "What is a business service?", "How does an application component relate to a data entity?" and "Which requirement led to this work package?".

Core and extensions

  • The core metamodel is the minimum set of entities and relationships needed for most architecture work.
  • Optional extensions add entities for specific needs, such as governance, process modelling or motivation, when the organization needs that extra detail.
  • Choosing which content to use is part of tailoring in the Preliminary Phase.

6. Functions, Services and Processes

Exam questions often test the difference between these business entities:

EntityMeaning
FunctionDelivers business capabilities, closely aligned to an organization but not necessarily explicitly governed by it
Business serviceSupports business capabilities through an explicitly defined interface and is explicitly governed by an organization
ProcessA flow of interactions between functions and services; shows how work is done in sequence

The same pattern repeats in each domain: business services are supported by information system services, which are supported by technology services.

7. From Metamodel to Artifacts

Artifacts are views over the metamodel:

  • A catalog lists instances of one entity type (e.g. all Physical Application Components).
  • A matrix shows the relationships between two entity types (e.g. Application Component × Function).
  • A diagram presents entities and relationships graphically for a particular stakeholder concern.

Because every artifact draws on the same metamodel, a repository tool can keep catalogs, matrices and diagrams consistent with each other.

The takeaway

  • The Content Framework gives a structural model for architecture content: the ADM is the how, the Content Framework is the what.
  • Content categories: deliverables contain artifacts, which describe building blocks.
  • The content metamodel defines entities and relationships for consistency, completeness and traceability, with a core and optional extensions.
  • Logical components are vendor-neutral (like ABBs); physical components are product-aware (like SBBs).
  • Function vs business service (explicit interface, explicitly governed) vs process (sequence of work).
  • Catalogs list one entity type; matrices relate two; diagrams show them graphically.
